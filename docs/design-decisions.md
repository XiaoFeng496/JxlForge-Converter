## 小图并行池的动态线程分配（搁置）

**状态**：搁置。当前采用简单版方案，待用户反馈后考虑迭代。

**背景**：双队列调度器中，小图并行池默认每图 1 线程。实践中发现对「少量中等图」
（如 3×12MP）每图 1 线程会浪费大量空闲核心（约 2× 的性能损失），因此考虑把
空闲核心均分给小图。

**简单版（当前采用）**：
批次开始按小图总数 `k` 一次性分配：
`nt = max(1, cores // min(k, cores))`
所有小图用同一 `nt`，O(1)、绝不超订，但进度中不重分配（末尾剩余文件仍只拿固定 nt）。

**动态版（搁置，待评估）**：
维护一个容量 = `cores` 的「核心槽」信号量。提交小图任务时申请 `nt` 个槽，凑满才放行、
用完释放。随文件完成，存活文件数减少，剩余文件自然抢到更多槽——末尾几张接近满核，
即实现「少文件 / 接近末尾时每图线程数 = 核心数 / 文件数」。

- 优点：精确利用空闲核心，末尾重分配收益最大。
- 缺点：实现更复杂（共享信号量、任务带期望 nt、释放需谨慎），还要与大图专属窗口衔接；
  且小图多线程扩展性差，动态版对「真小图」收益有限，主要惠及中等图。
- 注意：**不能用「每张提交时按剩余数独立重算 nt」的写法**，会导致瞬时总线程超订
  （例：4 图 20 核分别算 5/6/10/20 = 41 > 20）。必须用信号量统一管控总量。

**决策**：先用简单版落地，收集真实批次的用户反馈后再决定是否升级为动态版。

## 大图/小图分类阈值旋钮（已定默认值 + 未来计划）

**已采用默认值（待调度器落地时生效）**：
- 相对判定 `RATIO = 2.5`：文件像素 > 2.5 × 批次中位数像素时判为大图。
- 绝对地板目标加速比 `= 2.0`：`T_floor` 由校准脚本按本机算出 = speedup S 首次达到 2.0 对应的分辨率(MP)。

**未来计划（值得保留）**：
当前不向用户暴露 RATIO 与目标加速比旋钮。若未来有用户反馈特定场景（如某类均匀大批次、
或某 CPU 型号）分类不适配，再考虑在「高级参数」区域开放这两个旋钮，供高级用户微调。
